# 기술 조사 및 실험 지침

## 목적과 기준

조사는 후보의 목적·기능·근거를 확인하고 실험할 질문을 정한다. 실험은 조건을 통제해 그 질문을 검증한다. 기능 구현은 채택할 계약을 명세로 정한 뒤 진행한다. 작업 순서와 커밋은 [작업 흐름](../workflow.md), 하네스의 역할은 [기술 방향 > 역할](strategy.md#역할)을 따른다.

기술 조사에서는 대상 프로젝트가 명시한 목적·지원 범위·제약과 실제 구현을 확인한다. 우리 요구에 대한 적합성 평가와 새 기능의 효과 검증은 그 조사 결과를 입력으로 별도 수행한다. 대상의 지원 범위 밖인 기능은 해당 없음으로 기록하고, 미확인이나 품질 실패와 구별한다. 프로젝트별 기능을 확인하기 전에 특정 생성 방식이나 도메인 지식을 필수 기능으로 가정하지 않는다.

아래 기록 형식과 분류는 이 프로젝트의 문서 규약이며 현재 버전은 1이다. 외부 표준으로 간주하지 않는다. 실제 저장소에 적용하면서 빠진 항목을 확인하고, 의미가 바뀌면 버전과 변경 이유를 남긴다. 기존 결과를 새 기준으로 평가한 경우 재평가 기록을 추가한다. 미확인·해당 없음과 그 이유를 허용하며 분류에 맞추기 위해 기능을 추측하지 않는다.

## 문서 책임과 목차

아래 순서는 조사 계획·개별 분석·조사 보고·실험 계획·실험 보고의 작업 순서다. 각 문서는 제목 하나와 표에 적힌 2단계 제목을 정확한 순서로 사용한다. 세부 분류는 3단계 제목으로 추가한다. README는 안내에만 사용한다.

| 위치 | 책임 | 2단계 제목 순서 |
| --- | --- | --- |
| `research/<topic>/plan.md` | 조사 범위와 후속 작업의 기준 | 기록 정보 → 조사 질문 → 범위와 제외 → 후보 선정 → 분석 기준 → 진행 순서 → 완료 조건 |
| `research/<topic>/sources/<source>.md` | 고정 버전 저장소의 분석 | 기록 정보 → 목적과 사용자 → 핵심 기능 → 실행 흐름 → 하네스 구성 → 근거와 한계 |
| `research/<topic>/report.md` | 후보 간 비교와 실험할 질문 | 기록 정보 → 조사 범위 → 비교 결과 → 재사용 후보 → 미확인 사항 → 다음 결정 |
| `experiments/<experiment>/plan.md` | 실행 전에 고정할 조건 | 기록 정보 → 질문과 가설 → 입력과 고정 조건 → 비교 조건 → 실행 순서와 예산 → 평가 기준 → 완료 조건 |
| `experiments/<experiment>/report.md` | 전체 실행의 결과와 판단 | 기록 정보 → 실행 범위 → 결과 → 실패와 제외 → 해석 → 결정과 한계 |

경로 이름은 영어 `kebab-case`를 사용한다. 저장소 분석의 파일명은 `owner-repository.md`처럼 식별 가능한 이름으로 정한다. 조사·실험 보고서는 같은 디렉터리의 계획을 입력으로 연결한다. 실행 기록·원본·측정 파일은 해당 실험 아래에 두고 보고서에서 연결한다. 다운로드 캐시와 재생성 가능한 중간 산출물은 Git에서 제외한다.

각 절에는 다음 내용을 기록한다. 아래 목록은 위 표의 문서 순서를 따른다.

- 조사 계획의 `조사 질문`에는 내려야 할 결정을, `범위와 제외`에는 대상과 미결정·임시 가정을 적는다. `후보 선정`에는 검색 경로·포함·제외 기준을, `분석 기준`에는 공통 비교 축을 적는다. `진행 순서`에는 의존성과 현재 위치를, `완료 조건`에는 필요한 근거와 다음 단계로 넘어갈 조건을 적는다.
- 저장소 분석의 `목적과 사용자`에는 해결하려는 문제와 사용 대상을, `핵심 기능`에는 실제 제공 기능과 적용 범위를 적는다. `실행 흐름`에는 입력·중간 표현·출력·설치 조건을, `하네스 구성`에는 아래 분석 축별 구성 요소와 연결을 적는다. `근거와 한계`에는 주장별 출처·확인 수준·미확인·사용 조건을 적는다.
- 조사 보고서의 `조사 범위`에는 확인한 후보와 제외 사유를, `비교 결과`에는 같은 축으로 정렬한 비교와 근거를 적는다. `재사용 후보`에는 기능·코드·하네스별 활용 가능성을, `미확인 사항`에는 추가 확인이 필요한 질문을 적는다. `다음 결정`에는 권고·근거·실험할 질문과 그 의존성을 적는다.
- 실험 계획의 `질문과 가설`에는 확인할 효과와 반증 조건을, `입력과 고정 조건`에는 픽스처·버전·가정·재현 조건을 적는다. `비교 조건`에는 기준군·변경 변수·적용 순서를, `실행 순서와 예산`에는 명령·환경·반복·비용·중단 조건·산출물 계약을 적는다. `평가 기준`에는 지표·측정 방식·분모·판정 기준·검토 주체를, `완료 조건`에는 필요한 실행과 실패·중단 시 종료 기준을 적는다.
- 실험 보고서의 `실행 범위`에는 계획 대비 실제 조건·변경 사유를, `결과`에는 실행별 근거와 집계값을 적는다. `실패와 제외`에는 누락 없이 실패·제외·중단과 분모를 적는다. `해석`에는 가설 지지 여부·불확실성·다른 설명을, `결정과 한계`에는 적용 범위·채택 또는 기각·남은 질문을 적는다.

## 기록 정보

첫 절은 JSON 코드 블록 하나로 메타정보를 기록한다. 메타정보는 파일 경로와 결합해 기록을 식별한다. 문서 본문에 같은 값을 수동으로 반복하지 않는다. 공통 필드는 아래 순서로 안내하며 JSON 키 순서는 검사하지 않는다.

| 필드 | 값과 의미 |
| --- | --- |
| `schema_version` | 기록 형식 버전, 현재 `1` |
| `recorded_at` | 시간대가 포함된 ISO 8601 기록 시각 |
| `status` | `planned`·`in-progress`·`complete`·`incomplete` 중 하나 |
| `inputs` | 저장소 루트 기준의 실제 입력 파일 경로 목록 |

`recorded_at`은 내용을 마지막으로 확인한 시각이다. 완료 상태에는 완료 근거를 본문에 남긴다. 실험 보고서에서 `complete`는 계획한 관측과 정리가 끝났다는 뜻이며, 모든 결과가 합격했다는 뜻은 아니다. 실패·제외·중단을 빠뜨리지 않는다.

저장소별 분석에는 다음 필드를 추가한다. 외부 수치는 기록 시각에 관측한 값이며 나중의 현재 값으로 해석하지 않는다.

| 필드 | 값과 의미 |
| --- | --- |
| `taxonomy_version` | 분석 분류 버전, 현재 `1` |
| `repository` | 원본 저장소의 HTTPS URL |
| `revision` | 확인한 Git 커밋의 전체 40자리 또는 64자리 해시 |
| `license` | 확인한 라이선스 식별자·설명 또는 `null` |
| `stars` | 확인한 비음수 정수 또는 `null` |
| `last_commit_at` | 확인한 마지막 커밋의 시간대 포함 시각 또는 `null` |
| `archived` | 보관 상태의 참·거짓 또는 `null` |
| `unknowns` | `null`인 필드별 확인하지 못한 이유 |
| `evidence_level` | `documented`·`code-inspected`·`executed` 중 가장 높은 확인 수준 |
| `evidence` | 확인한 문서·코드의 HTTPS URL 목록 |

코드 확인과 실행 확인에는 동일 커밋이 포함된 근거 URL이 필요하다. 실행 확인은 입력 목록에 로컬 실행 증거도 연결한다. 높은 확인 수준이 모든 기능에 적용되는 것은 아니므로 본문의 각 주장에도 근거와 확인 수준을 붙인다. 별 수만으로 품질이나 유지보수 상태를 판정하지 않는다. 라이선스는 코드·모델·에셋의 조건을 구분한다.

## 후보 선정과 분석

조사 계획은 목적 적합성·사용 사례·인기도·최근 유지보수·실행 가능성·사용 조건을 기준으로 후보를 고른다. 검색 날짜와 검색 범위, 포함·제외 이유를 남긴다. 인기와 관련성은 별도로 판단하고 특정 생성 경로만 조사하지 않는다.

저장소별 분석은 실제 작업의 입력부터 출력까지 추적한다. 구성 요소마다 다음 축을 같은 순서로 기록한다.

1. 담당 기능과 입력·출력·연결 위치를 기록한다.
2. Guide·Sensor·Gate·Transformer 중 실제 역할을 기록한다. 여러 역할을 허용한다.
3. 코드·모델·사람 중 판정 주체와 Verification·Eval의 기준을 기록한다.
4. 성공·규칙 위반·검사 오류·미검증 상태와 그 근거를 기록한다.
5. 계속 진행·수정·재생성·사람에게 결정 요청·중단 중 다음 행동과 반복 한도를 기록한다.
6. 해당 코드·설정·테스트·실행 결과를 연결하고 확인 범위를 기록한다.

역할 분류와 판정 방법, 다음 행동은 서로 다른 축이다. 검사 코드가 존재해도 실제 실행 경로에 연결되지 않았으면 차단 장치로 기록하지 않는다. 문서 설명·코드 확인·실행 확인을 구분하며, 실행 후 검사로 이전 실행의 부작용을 막았다고 기록하지 않는다.

## 실험과 평가

실험 전에 입력·픽스처·모델·도구 버전·고정 조건·비교 변수·순서·반복·예산·중단 조건·평가 기준을 기록한다. 결과를 본 뒤 조건을 바꾸면 별도 비교로 분리한다. 생성 결과의 고정과 정상 품질의 검증을 구별한다. 전체 파이프라인 비교와 요소 하나의 적용 유무 비교도 구별한다.

전체 성공률의 분모에는 실패·시간 초과·중단을 포함한다. 정상·실패 사례를 함께 평가하고 오탐·누락·사람의 수정 시간·재시도 비용을 기록한다. 같은 개체의 프레임이나 반복 생성을 독립 개체의 표본 수로 세지 않는다. 탐지기를 조정한 사례와 최종 평가 사례를 분리한다.

실행별 상세 기록에는 시각·실행 명령·환경·코드 버전·도구와 모델 식별자·생성 지침·설정·입출력 파일 경로와 해시·사용량·판정·오류를 남긴다. 외부 서비스의 정확한 모델 버전·시드가 노출되지 않으면 이유를 기록한다. 재생성 가능한 조건과 재생성해도 달라질 수 있는 조건을 구분한다. 실행별 산출물 계약은 해당 실험 계획에서 먼저 정의한다. 현재 공통 검사기는 Markdown 기록의 형식과 연결을 검사하며 모든 실험 산출물 형식을 검사하지 않는다.

## 검사와 피드백

자동 검사는 [작업 기록 검사](../../specs/workflow-checks/spec.md)를 따른다. 형식 통과는 근거의 진실성이나 분석의 완전성을 보장하지 않는다. 별도 검토에서 문서 책임·분류의 적용·증거의 주장 뒷받침·비교 조건·미확인 항목을 확인한다.

경로·누락·순서 등 확인 가능한 오류는 근거를 찾아 수정하고 재검사한다. 같은 실패의 자동 수정은 최대 3회로 제한한다. 검사기 오류나 한도 초과를 통과로 바꾸지 않고 원인과 남은 상태를 기록한다. 사용자 선택·권한·요구 변경이 필요한 경우에만 결정할 사항과 시도한 내용을 제시한다. 분석값을 채우기 위한 추측이나 임의 수정은 하지 않는다.

현재 하네스는 문서 Guide, 검사 결과 Sensor, 구조 Verification과 CI 실패 출력을 제공한다. 자동 Transformer와 호스트 실행 전 차단은 제공하지 않는다. 원격 CI 실행과 필수 검사 설정을 확인하기 전에는 병합 Gate가 작동한다고 보고하지 않는다.
