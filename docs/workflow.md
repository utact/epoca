# 작업 흐름

사람과 에이전트가 함께 사용하는 개발 절차다. SDD(Spec-Driven Development)에 따라 요구사항과 수용 기준을 먼저 정하고, 구현 후에도 명세를 갱신한다.

## 문서 책임

| 위치 | 책임 |
| --- | --- |
| [게임 설계](game/design.md) | 게임 목표와 규칙 |
| [게임 검증](game/validation.md) | 실패 조건·검증 방법·측정 항목 |
| [미결정 사항](game/open-questions.md) | 미결정 정책·수치·방식 |
| [기술 방향](engineering/strategy.md) | 공통 기술 제약과 개발 방향 |
| `specs/<feature>/spec.md` | 기능의 구현 범위·관찰 가능한 동작·수용 기준 |
| `specs/<feature>/design.md` | 구현 구조·인터페이스·기술 선택과 근거 |
| `specs/<feature>/plan.md` | 해당 변경의 작업 순서·진행 상태·검증 결과 |
| `experiments/<experiment>/` | 가설을 검증한 실험의 코드·입력·결과 |
| `tests/` 또는 구현 코드 옆의 테스트 | 명세를 반복해서 확인하는 실행 가능한 검사 |

게임 규칙과 수치는 게임 설계에서 정의한다. 기능 명세는 관련 규칙을 링크하고 해당 기능의 동작과 수용 기준을 구체화한다. 기술 설계나 실험 결과로 게임 규칙을 덮어쓰지 않는다.

## 작업 순서

1. 관련 기준 문서, 미결정 사항, 현재 구현을 확인한다.
2. 결정이 필요하면 선택지와 판단 기준을 정한다. 실험은 임시 가정을 명시해 진행한다.
3. 구현할 동작과 수용 기준을 명세에 적고 확인 방법을 정한다.
4. 필요한 구현 설계와 작업 순서를 정한 뒤 구현한다.
5. 검사 결과를 수용 기준과 대조하고 문서·코드·검증의 정합성을 확인한다.

기존 기능 명세로 설명되는 작은 수정은 해당 명세를 사용한다. 새 기능 명세가 필요하면 `spec.md`부터 작성한다. 검토 중인 문서는 제목 아래에 `상태: 초안`을 표시한다. 별도로 유지할 구현 설계나 여러 단계의 작업이 있을 때 `design.md`, `plan.md`를 추가한다. 디렉터리는 실제 파일이 필요할 때 만든다.

## 검증 수단

| 수단 | 확인 대상 |
| --- | --- |
| 자동 테스트 | 명세 충족 여부와 회귀 발생 여부 |
| 게임 실험 | 플레이어 행동과 시간 경과가 적응·경제 등에 미치는 영향 |
| 플레이 테스트 | 플레이어의 결과 인지·이해·대응 |
| 에이전트 Eval | 작업 사례 집합에서 에이전트·도구·지시 변경의 효과 |

판정에 필요한 입력, 지표 정의, 허용 범위는 실행 전에 정한다. 아직 정할 수 없는 항목은 탐색 결과로 기록하고 통과로 판정하지 않는다.

실험 기록에는 가설, 가정, 입력·난수 시드·코드 버전·실행 방법, 결과·판정·한계를 남긴다. 플레이 테스트에는 과제와 참여 조건을 남긴다. 결과의 유효 범위는 실행한 버전과 조건으로 한정한다.

## 변경과 완료

- 결정은 해당 기준 문서에 반영하고 해결된 미결정 항목을 제거한다. 기능에만 해당하는 질문은 해당 명세에서 관리한다.
- 요구사항을 바꾸면 참조하는 명세·설계·테스트를 확인해 같은 변경에서 갱신한다. 파일이나 절을 옮길 때는 들어오는 링크도 갱신한다.
- 채택한 명세와 필요한 구현 설계는 현재 기준으로 유지한다. 폐기한 대안과 이전 규칙은 Git 이력으로 남긴다.
- 작업 계획은 해당 변경에만 적용한다. 완료 시 검증 결과를 남기고, 다음 변경에서는 계획을 갱신한다. 계속 필요한 설계 근거는 구현 설계에 둔다.
- 검증 결과는 작업 계획에, 계획이 없는 작은 수정은 변경 설명에 기록한다. 실험 결과는 실험 디렉터리에 두고 링크한다.
- 완료는 해당 변경의 수용 기준을 확인한 상태다. 미실행·실패 항목은 남은 작업으로 표시한다.

## 작성 기준

- 한 사실의 기준 문서는 한 곳으로 정한다. 다른 문서에서는 링크하고 필요한 맥락만 요약한다.
- 한 항목의 주제를 하나로 좁히고 관련 조건은 함께 적는다.
- 필수 동작과 선택 기능을 구분한다. 후보나 예시만으로 기능 도입을 확정하지 않는다.
- 같은 개념은 기준 문서의 용어로 쓴다. 기술명과 의미가 더 명확한 영어 용어는 그대로 쓴다.
- 항목을 나열할 때는 목록 전체의 목적과 정렬 기준을 먼저 정한다. 조회용 목록은 전체를 이름순으로 정렬한다. 비교용 목록은 모든 항목의 그룹 기준과 그룹 안의 대응 순서를 정한다. 일부 항목만 대응쌍으로 묶고 나머지를 이름순으로 덧붙이지 않는다.
- 직접 정하는 파일·디렉터리 이름은 영어 `kebab-case`를 쓴다. `README.md`, `AGENTS.md`, `CLAUDE.md` 등 도구가 사용하거나 관례로 정한 이름은 유지한다.

### 문체와 마커

| 대상 | 표기 |
| --- | --- |
| 설명·규칙·실패 조건·검증 방법 | 한다체의 완결된 문장, 문장 끝 마침표 |
| 제목·표 셀·미결정 항목·측정 항목 | 명사구, 마침표 생략 |
| 제목 계층 | 문서 제목 `#`, 영역 `##`, 하위 항목 `###` |
| 순서 없는 목록 | `-` |
| 순서 있는 목록 | `1.`, `2.`처럼 순서대로 증가하는 번호 |
| 작업 계획의 진행 상태 | 미완료 `- [ ]`, 완료 `- [x]` |
| 문서 링크 | 대상 문서의 제목과 같은 표시명 |
| 절 링크 | `문서 제목 > 절 제목` 형식의 표시명 |

표는 같은 열의 표현 형식을 맞춘다. 설명은 `충족 여부`, `마침표 생략`처럼 명사구로 쓰고, 코드·경로·마커는 원래 표기를 유지한다.

- 표에서는 문장의 끝만 줄이지 않고 항목의 핵심을 명사구로 표현한다. 같은 열에서는 대상·조건·결과를 배열하는 구조도 맞춘다.
- 수용 기준은 충족해야 할 상태나 성질을 명사구로 표현한다. `여부`는 확인 대상에 사용하며, 수용 기준에서는 합격 조건을 명확히 적는다.
- 명사구로 줄이면 조건이나 의미가 흐려지는 설명은 표 밖에 완결된 문장으로 적는다.

다음은 개인 색상 선택 초안에서 실제로 수정한 사례다. 사례 간 대칭을 위해 원문을 바꾸지 않는다.

| 수정 전 | 수정 후 |
| --- | --- |
| `동시 추첨과 확정에서 같은 색의 소유자가 중복되지 않음` | 동시 추첨·확정 시 색상 소유권의 유일성 |
| `여러 탭과 연타로 정해진 추첨 횟수를 초과하지 않음` | 여러 탭·연타 시 추첨 횟수 상한 준수 |
| `만료·재방출된 색을 이전 선택 상태로 확정할 수 없음` | 만료·재방출 후 이전 선택 상태에 의한 색상 확정 차단 |
| `유사색·어두운 색·밝은 색에서도 닉네임과 본문을 읽을 수 있음` | 유사색·어두운 색·밝은 색에서 닉네임과 본문의 가독성 확보 |

절 링크는 제목에서 생성되는 앵커를 사용한다. 개별 규칙에 대한 참조가 필요할 때만 영어 `kebab-case`의 HTML 앵커를 추가한다. 숨은 주석을 참조 마커로 사용하지 않는다.

### 코드 주석

- 주석은 코드만으로 알기 어려운 이유·제약·출처를 설명한다. 코드나 함수 이름을 그대로 풀어 쓰는 설명은 생략한다.
- 주석은 적용 대상 바로 위에 둔다. 일부 항목에만 해당하는 설명을 전체 함수나 자료의 설명처럼 배치하지 않는다.

### 예시와 테스트 데이터

- 예시와 테스트 데이터는 비교 기준별로 묶고, 같은 묶음에서는 이름·문장 구조·자료형·단위를 맞춘다.
- 대립하는 상태는 같은 대상의 대응쌍으로 나란히 제시한다. 존재·부재, 성공·실패, 허용·차단 순서를 기본으로 사용한다.
- 수치의 경계 사례는 경계 직전·경계값·경계 직후 순서로 나열한다. 값을 임의로 흩어 놓지 않는다.
- 비교하는 사례에서는 확인하려는 조건만 바꾼다. 여러 조건의 조합을 검증할 때는 조합 기준을 밝힌다.
- 문구 수정 예시는 원문과 수정문을 짝짓고, 테스트 사례에는 입력과 기대 결과를 함께 둔다.
- 실제 오류를 재현하는 회귀 사례는 원문을 보존한다. 정상 대조 사례와 일반 예시를 구분하고, 형식 대칭만을 위해 의미 없는 사례를 추가하지 않는다.
- 하네스의 규칙과 예시는 [기술 방향 > 규칙과 퓨샷](engineering/strategy.md#규칙과-퓨샷)에 따라 설계하고 검토한다.
- 순서 자체를 검증하지 않는 무작위 데이터는 재현 가능한 시드를 사용한다. 임시 파일 이름 등 충돌 방지용 값은 검사 결과의 기대값과 분리한다.

| 비교 기준 | 나열 순서 | 예시 |
| --- | --- | --- |
| 존재 상태 | 존재 → 부재 | `색상 존재` → `색상 부재` |
| 처리 결과 | 성공 → 실패 | `요청 성공` → `요청 실패` |
| 접근 상태 | 허용 → 차단 | `접근 허용` → `접근 차단` |
| 수치 경계 | 직전 → 경계값 → 직후 | `상한 - 1` → `상한` → `상한 + 1` |

### 문서 변경 검사

문서를 수정한 작업은 완료 전에 저장소 루트에서 `python scripts/check-docs.py`를 실행한다. Python 3.12 이상과 Git을 사용하며 추가 패키지는 필요하지 않다. 자동 검사 범위와 오류 코드는 [문서 표기 검사](../specs/docs-style/spec.md)를 따른다.

자동 검사 통과 후에는 변경한 문서에서 다음 항목을 직접 검토한다. 검사 실행이 불가능하면 미실행 이유를 보고하며, 통과로 기록하지 않는다.

- 설명·규칙의 완결된 문장과 문장 끝 마침표
- 제목·표 셀·미결정 항목·측정 항목의 명사구 표현
- 같은 표 열의 표현 형식과 구체성 수준
- 나열한 항목의 분류 기준·항목 수준·정렬 순서
- 표현을 줄이는 과정에서 조건·부정·예외의 의미 보존
- 수용 기준의 명확한 합격 조건과 확인 방법의 대응
- 예시의 분류 기준·대응 관계·나열 순서

완료 보고에는 자동 검사 결과와 문체 검토 결과를 구분해 적는다. 자동 검사 통과만으로 문서 규약 전체를 충족했다고 판단하지 않는다.

검사기를 변경할 때는 `python tests/docs-style/test-check-docs.py`도 실행한다. 실제 위반 사례와 정상 표현을 회귀 테스트에 함께 추가한다. 예외를 넓혀 오류를 숨기거나 기존 규약을 검사기의 탐지 범위에 맞춰 축소하지 않는다.

테스트 데이터를 추가하거나 수정할 때도 [작업 흐름 > 예시와 테스트 데이터](#예시와-테스트-데이터)의 분류·대응·순서를 검토한다. 이 항목은 표기 검사기의 자동 판정 범위에 포함하지 않는다.

### 게임 검증 양식

각 검증 영역은 관련 규칙을 `참조:` 링크로 밝히고 다음 하위 제목을 같은 순서로 사용한다.

1. `실패 조건`: 설계가 의도와 어긋났다고 판단할 상황
2. `검증 방법`: 입력·비교 조건·실행 절차와 자동 테스트
3. `측정 항목`: 판정에 사용할 지표와 관찰 기록

검증 방법에는 수치 실험·자동 테스트·플레이 테스트를 포함한다. 지표 정의와 허용 범위는 실험별로 정하고, 실행 결과는 실험 기록에 남긴다.
